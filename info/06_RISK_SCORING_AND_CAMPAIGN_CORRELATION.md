# Risk Prioritization Engine & Campaign Correlation
## 4-Factor Scoring Formula, Triage Categories & Kill-Chain Tracking

This document explains how heterogeneous alerts from Suricata signatures and Machine Learning models are normalized into a unified $[0, 100]$ operational threat priority score, and how multi-stage attack campaigns are automatically correlated.

---

## 1. The Operational Problem: SOC Alert Fatigue

In modern Security Operations Centers (SOCs), analysts receive thousands of raw alerts daily. Most commercial tools report raw binary classifications or disparate vendor severity labels (e.g., "Priority 2" from Suricata vs "0.91 Probability" from an ML model). 

This disparity creates two problems:
1. **Incomparable Alerts:** An analyst cannot easily determine whether a Priority 2 Suricata alert is more urgent than an ML alert with probability 0.85.
2. **Alert Fatigue:** High-volume alerts without operational context force analysts to investigate alerts in random order, allowing severe multi-stage breaches to go unaddressed.

To solve this, our backend implements an authoritative **4-Factor Risk Scoring Engine** (`backend/app/risk_engine.py`) configured through `config.yaml`.

---

## 2. The 4-Factor Risk Scoring Formula

Every alert generated by the system is evaluated using the following weighted linear heuristic:

$$\text{RiskScore} = \text{round}\Big(100 \times \big(0.40 \cdot S_{\text{sev}} + 0.30 \cdot S_{\text{conf}} + 0.20 \cdot S_{\text{beh}} + 0.10 \cdot S_{\text{ctx}}\big), 1\Big)$$

Where each factor $S \in [0.0, 1.0]$:
* **$S_{\text{sev}}$ (Severity, weight 40%):** How inherently dangerous is the attack type?
* **$S_{\text{conf}}$ (Confidence, weight 30%):** How certain is the detection engine of its verdict?
* **$S_{\text{beh}}$ (Behavior, weight 20%):** How anomalous or aggressive is the physical flow traffic?
* **$S_{\text{ctx}}$ (Context, weight 10%):** How critical is the target destination asset?

---

## 3. Deep Dive into the 4 Factors

### Factor 1: Severity ($S_{\text{sev}}$)
* **For Signature Alerts:** Severity is mapped directly from Suricata's rule priority:
  * Priority 1 (Root, RCE, Remote Exploits) -> $S_{\text{sev}} = 0.95$
  * Priority 2 (SQLi, Traversal, Scanning) -> $S_{\text{sev}} = 0.68$
  * Priority 3 (Policy Violations, Informational) -> $S_{\text{sev}} = 0.36$
  * Priority 4 (Audit Events) -> $S_{\text{sev}} = 0.18$
* **For ML Alerts:** Baseline severity is set to $0.58$. However, for volumetric floods, severity dynamically scales up to $0.92$ based on packet rate and TCP flag intensity:
  $$S_{\text{sev}} = \min\big(0.92, 0.58 + 0.20 \cdot \frac{\text{flow\_packets\_s}}{5000} + 0.14 \cdot \frac{\text{syn\_flag\_count}}{50}\big)$$

### Factor 2: Confidence ($S_{\text{conf}}$)
* **For Signature Alerts:** Base confidence is $0.78$ (or $0.90$). Bonuses are awarded for corroborating evidence:
  * $+0.06$ per additional matched pattern in the payload (up to $+0.12$).
  * $+0.04$ if the destination port matches the standard service port.
  * $+0.03$ if bidirectional return packets are observed.
* **For ML Alerts:** Confidence is set directly to the Platt-calibrated posterior probability:
  $$S_{\text{conf}} = P(\text{malicious} \mid \mathbf{x})$$

### Factor 3: Behavior ($S_{\text{beh}}$)
Computed via `compute_behavior_score()` based on four physical flow indicators:
1. **Rate Factor (Weight 70%):** Measures packet throughput ($/1200\text{ pkts/s}$) and byte rate ($/800\text{ KB/s}$).
2. **Flag Factor (Weight 18%):** Measures saturation of SYN, RST, and PSH flags ($/20\text{ flags}$).
3. **Asymmetry Factor (Weight 7%):** Measures ratio of forward packets to backward response packets (high asymmetry indicates one-way flooding or un-replied scanning).
4. **Variance Factor (Weight 5%):** Packet size variance normalized against typical mixed-traffic profiles.

### Factor 4: Asset Context ($S_{\text{ctx}}$)
Assesses the organizational criticality of the destination port:
* **High-Value Administrative / Database Ports (Score 0.86):** Port 22 (SSH), 3389 (RDP), 445 (SMB), 1433 (MSSQL), 3306 (MySQL), 5432 (Postgres). Compromise of these services results in full infrastructure takeover.
* **Production Web Services (Score 0.74):** Port 80 (HTTP), 443 (HTTPS), 8080, 8443.
* **Privileged Ports (< 1024) (Score 0.58):** Standard system daemon ports.
* **Ephemeral Ports (Score 0.32):** High ports (> 1024) without known critical daemons.

## 4. Multi-Stage Kill-Chain Campaign Correlation

Advanced Persistent Threats (APTs) rarely execute a single isolated action. A typical breach involves a multi-stage kill chain:
1. **Reconnaissance:** High-speed port sweep or vulnerability scan to discover open ports.
2. **Weaponization & Delivery:** Sending an application exploit (e.g., Log4j or SQLi) to compromise the server.
3. **Exfiltration / Flood:** Data exfiltration or volumetric denial-of-service.

### The Correlation Window:
In `backend/app/main.py`, `apply_multi_stage_campaign_correlation()` tracks all alerts generated within a sliding **60.0-second time window** (`campaign_correlation_window_sec`).

```text
Attacker IP 198.51.100.44
       |
       +---> Time 12:00:01: ML Port Scan Alert on Port 443 (Risk = 62.4, High)
       |
       +---> Time 12:00:15: Suricata Log4j Exploit on Port 8080 (Risk = 74.2, High)
       |
       +-------------------------------------------------------------+
       | CORRELATION ENGINE DETECTS:                                 |
       | - Same Source IP within 60 seconds                          |
       | - Multi-Stage Kill Chain: ML Recon + Signature Exploit      |
       |                                                             |
       | ELEVATION ACTION:                                           |
       | 1. Boosts Context Factor: S_ctx -> 1.00 for both alerts     |
       | 2. Elevates Risk Scores: 74.2 -> 88.0 (CRITICAL)            |
       | 3. Unifies alerts under Campaign ID: "cmp-198-51-100-44"   |
       +-------------------------------------------------------------+
```

### The Explanation Output:
The alert explanation dynamically reflects the correlated kill-chain evidence:
> `[Multi-Stage Kill-Chain Correlated (cmp-198-51-100-44): 2 alerts from 198.51.100.44 across Stage 1: Reconnaissance (ML) + Stage 2: Payload Exploitation (Log4j RCE) boosted context 0.74 -> 1.00, elevating score to 88.0/100 (Critical).]`

## 5. Triage Categories & SOC Analyst Workflow

Risk scores map into four operational urgency tiers:

| Risk Score Range | Priority Category | Recommended SOC Action | Typical Trigger Examples |
| :---: | :---: | :--- | :--- |
| **0.0 - 29.9** | **Low** | Log for forensic audit; no immediate paging | Minor protocol deviations, routine web spiders |
| **30.0 - 59.9** | **Medium** | Queue for scheduled review | Single-packet port probe, low-confidence anomaly |
| **60.0 - 79.9** | **High** | Triage within 15 minutes; examine target host | Standalone SQLi attempt, uncorroborated volumetric flood |
| **80.0 - 100.0** | **Critical** | Immediate incident response; automated isolation | Correlated multi-stage kill chains, verified Log4j RCE, root exploits |

### Analyst Lifecycle State Machine:
To support real-world SOC workflows, each alert record in SQLite maintains an analyst triage state:
* `open` (Default): Alert newly created by the pipeline, awaiting investigation.
* `confirmed`: Analyst has investigated the packet evidence, validated the threat, and escalated the incident.
* `false_positive`: Analyst determined the transaction was benign business activity. Analysts can persist written justification notes directly to the alert record via `PATCH /api/alerts/:id/status`.
