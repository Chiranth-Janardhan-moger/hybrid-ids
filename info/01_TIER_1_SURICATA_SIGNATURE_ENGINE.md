# Tier 1 Defense: Suricata Signature-Based Engine
## Deterministic Deep Packet Inspection & Correlation

This document provides a comprehensive technical study of **Tier 1** in the Hybrid IDPS pipeline: the **Suricata Signature-Based Detection Engine**.

---

## 1. What is Signature-Based Detection?

Signature-based Network Intrusion Detection (also known as misuse detection) relies on a database of pre-compiled rules or signatures that describe known attack patterns. When a network packet arrives, the engine inspects packet headers and application-layer payloads (Deep Packet Inspection or DPI) against these rules. If an exact byte sequence, regular expression, or protocol anomaly matches a rule, an alert is triggered immediately.

### Key Characteristics of Tier 1:
* **Deterministic:** A given packet either matches a rule or it does not. There is no probabilistic guesswork.
* **Near-Zero False Positives:** Well-written rules for specific exploit payloads (e.g., Log4j JNDI lookups or SQL injection syntax) produce almost zero false alarms on normal business traffic.
* **High Explainability:** When an alert fires, the Security Operations Center (SOC) analyst immediately receives the exact Signature ID (SID), CVE number, classification type, and the exact offending byte string.

## 2. Suricata Architecture & Rule Mechanics

Suricata is a high-performance, multi-threaded open-source Network Threat Detection engine capable of real-time intrusion detection (IDS), inline intrusion prevention (IPS), and network security monitoring (NSM).

### Rule Syntax Breakdown
Suricata rules follow a standard header-and-options structure:

```text
action proto src_ip src_port -> dst_ip dst_port (options)
```

For example, consider the Apache Log4j rule implemented in `suricata/rules/local.rules`:

```text
alert tcp any any -> any any (msg:"ET EXPLOIT Apache Log4j RCE Attempt (CVE-2021-44228)"; flow:established,to_server; content:"${jndi:"; nocase; classtype:attempted-admin; sid:2034647; priority:1; rev:1;)
```

#### Rule Field Breakdown:
* **`alert`:** The action to take. In IDS mode, an alert record is emitted into `eve.json`.
* **`tcp any any -> any any`:** Matches TCP packets traveling from any source IP and port to any destination IP and port.
* **`msg:"..."`:** The human-readable description displayed to the SOC analyst.
* **`flow:established,to_server`:** Enforces TCP state tracking. Suricata ignores initial SYN handshakes and evaluates the rule only after the 3-way handshake completes and data flows toward the server.
* **`content:"${jndi:"`:** The exact byte payload pattern that triggers the rule.
* **`nocase`:** Case-insensitive match (catches `${JNDI:`, `${jndi:`, etc.).
* **`classtype:attempted-admin`:** Categorizes the threat in accordance with standard taxonomy (attempt to gain administrator privileges).
* **`sid:2034647`:** Unique Suricata Identifier.
* **`priority:1`:** Suricata severity ranking:
  * Priority 1: High severity (RCE, root exploits, command execution)
  * Priority 2: Medium severity (trojan activity, scanning, SQLi)
  * Priority 3: Low severity (informational, reconnaissance, minor policy violations)
  * Priority 4: Very low / audit logging

## 4. 5-Tuple and Time-Window Flow Correlation

A major architectural challenge in hybrid systems is: **How do we link an alert generated by Suricata (which inspects individual packets) to a bidirectional statistical network flow (which aggregates entire conversations)?**

The correlation algorithm is implemented in `suricata/runner.py` via `correlate_alerts_to_flows()`:

```python
def correlate_alerts_to_flows(flows, eve_alerts, time_window_sec=5.0):
    matches = {}
    for idx, fl in enumerate(flows):
        f_tuple_fwd = (fl["src_ip"], fl["src_port"], fl["dst_ip"], fl["dst_port"], fl["protocol"])
        f_tuple_bwd = (fl["dst_ip"], fl["dst_port"], fl["src_ip"], fl["src_port"], fl["protocol"])
        
        for alert in eve_alerts:
            a_tuple = (alert["src_ip"], alert["src_port"], alert["dst_ip"], alert["dst_port"], alert["protocol"])
            
            # 1. Bidirectional 5-Tuple Check
            if a_tuple in (f_tuple_fwd, f_tuple_bwd):
                # 2. Temporal Window Check (+/- 5.0 seconds)
                if (fl["start_ts"] - time_window_sec) <= alert["timestamp"] <= (fl["end_ts"] + time_window_sec):
                    matches[idx] = alert
                    break
    return matches
```

### Why Bidirectional Matching is Essential:
In TCP traffic, the client sends request packets (`src_ip:port -> dst_ip:port`) and the server replies (`dst_ip:port -> src_ip:port`). An exploit signature might fire on a client request (e.g., an HTTP GET containing SQL injection) or on a server response (e.g., a database error string). By checking both forward and backward 5-tuples, the engine ensures that the entire flow conversation is linked to the alert regardless of which direction carried the payload.

### Why a 5.0-Second Time Window:
Network latency, buffering, and multi-packet reassembly can cause small timestamp offsets between when the first packet of a flow is captured and when Suricata's reassembly engine emits the alert. A `5.0s` sliding correlation window eliminates clock jitter false negatives without allowing unrelated sessions to cross-contaminate.

## 5. Severity & Confidence Mapping

When Suricata fires, its raw metadata is normalized for the Risk Scoring Engine:

### Priority to Severity Mapping:
Suricata priorities (1 to 4) are mapped into normalized decimal values $[0.0, 1.0]$ via `config.yaml`:
* Priority 1 (Root / RCE / Critical Exploit) -> `Severity = 0.95`
* Priority 2 (SQLi / Traversal / Trojan Activity) -> `Severity = 0.68`
* Priority 3 (Reconnaissance / Policy Violation) -> `Severity = 0.36`
* Priority 4 (Informational / Low Severity) -> `Severity = 0.18`

### Base Confidence:
Because signature matches are deterministic payload matches, Tier 1 alerts receive a high baseline confidence:
* Base Confidence = `0.78` (or `0.90` in demo configurations)
* **Confidence Bonuses:**
  * Additional matched patterns: $+0.06$ per extra pattern (up to $+0.12$)
  * Privileged target port (e.g., port 22, 443, 3306): $+0.04$
  * Backward response packets present: $+0.03$
* Resulting confidence routinely reaches `0.92 - 0.98`.

## 6. Strengths and Inherent Limitations of Tier 1

### Strengths:
1. **Precise Root Cause:** Points directly to the payload string (e.g., `SID 2034647: ${jndi:ldap://...}`).
2. **Instant Defense Against Known Threats:** Zero training data required. If an exploit has a CVE and an ET Open rule, Suricata stops it immediately.
3. **High Throughput:** Multi-threaded Hyperscan pattern matching allows scanning gigabits per second of known signatures.

### Inherent Limitations:
1. **Zero-Day Blindness:** If an attacker modifies the exploit syntax, uses a novel zero-day payload, or attacks an unpublished vulnerability, no signature exists and Tier 1 passes the packet as clean.
2. **Payload Encryption (TLS/HTTPS):** Without full SSL/TLS termination and decryption proxies, packet payloads are cipher text. Suricata cannot inspect inside encrypted HTTPS payloads for SQLi or Log4j strings.
3. **Volumetric / Behavioral Blindness:** High-rate TCP SYN floods, UDP floods, and Slowloris connection starvation attacks use completely valid packet headers without any malicious payload bytes. Signatures cannot detect these attacks.

**Conclusion:** Tier 1 is mandatory for stopping known exploits with near-zero false alarms, but it cannot defend the network alone. Unmatched traffic must cascade into **Tier 2 (Machine Learning)**.
